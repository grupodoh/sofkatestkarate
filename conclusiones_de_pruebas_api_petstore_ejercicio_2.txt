HALLAZGOS Y CONCLUSIONES - EJERCICIO 2: PRUEBAS DE API REST (SWAGGER PETSTORE)

1. RESUMEN EJECUTIVO
--------------------
Se implementaron las pruebas automatizadas con Karate Framework para validar el 
flujo CRUD de usuarios en la API pública de PetStore (https://petstore.swagger.io/v2). 
Se cubrieron los 5 casos solicitados en secuencia, revisando los códigos HTTP, 
la estructura de las respuestas y el paso de variables entre peticiones. Durante 
la ejecución se detectaron comportamientos irregulares propios del entorno de 
pruebas en la actualización y eliminación de registros.

2. ANÁLISIS POR CASO DE PRUEBA (ENTRADAS, SALIDAS Y VARIABLES)
--------------------------------------------------------------

2.1. Crear un usuario (POST /v2/user)
  * Entradas: JSON con los campos id, username, firstName, lastName, email, 
    password, phone y userStatus.
  * Manejo de Variables: Se usaron datos dinámicos (timestamp/UUID) para el 
    'username' y el 'id' con el fin de evitar choques con otros usuarios en 
    el servidor público. El 'username' se guardó en una variable para usarlo 
    en las siguientes peticiones.
  * Salidas: Responde con HTTP 200 OK y el cuerpo:
    { "code": 200, "type": "unknown", "message": "<id_del_usuario>" }.

2.2. Buscar el usuario creado (GET /v2/user/{username})
  * Entradas: Parámetro de ruta '{username}' obtenido del paso anterior.
  * Salidas: Responde con HTTP 200 OK y el objeto JSON del usuario. Se validó 
    con 'match' que el username, firstName y email coincidieran con los datos 
    enviados en la creación.

2.3. Actualizar el nombre y el correo del usuario (PUT /v2/user/{username})
  * Entradas: Parámetro de ruta '{username}' y el JSON del usuario con los 
    nuevos valores en 'firstName' y 'email'.
  * Salidas y Hallazgo: Aunque el servicio responde con código HTTP 200 OK, 
    presenta un fallo interno y no aplica los cambios en la base de datos. 
    Es un falso positivo donde la API confirma la recepción de la petición 
    pero descarta o no persiste la modificación. Además, si no se envía el 
    objeto completo, tiende a sobrescribir los campos omitidos.

2.4. Buscar el usuario actualizado (GET /v2/user/{username})
  * Entradas: Parámetro de ruta '{username}'.
  * Salidas y Hallazgo: Responde con HTTP 200 OK, pero al revisar el cuerpo 
    de la respuesta se comprueba que el 'firstName' y el 'email' siguen teniendo 
    los valores iniciales de la creación, confirmando que el PUT anterior no 
    tuvo efecto real.

2.5. Eliminar el usuario (DELETE /v2/user/{username})
  * Entradas: Parámetro de ruta '{username}'.
  * Salidas y Hallazgo: Al ejecutar la eliminación del registro creado, la API 
    responde con código HTTP 404 Not Found. Esto ocurre porque el entorno 
    compartido de PetStore no mantiene la persistencia estable entre sesiones 
    o elimina/resetea registros en memoria rápidamente, haciendo que el recurso 
    ya no esté disponible cuando se intenta borrar.

3. HALLAZGOS GENERALES SOBRE LA API DE PETSTORE
-----------------------------------------------
  * Falsos Positivos y Falta de Persistencia: El problema principal encontrado 
    es la inconsistencia entre el código HTTP y el estado real de los datos. 
    El PUT devuelve 200 sin guardar los cambios y el DELETE falla con 404 sobre 
    un usuario recién consultado. En una prueba automatizada esto obliga a no 
    confiar únicamente en el status 200, sino a validar siempre con un GET 
    posterior.
  * Inestabilidad del Servidor Público: Al ser un ambiente de demostración 
    abierto a nivel global, la concurrencia y el reinicio constante de datos 
    en caché provocan que los registros desaparezcan o no se actualicen de 
    forma predecible.
  * Seguridad Abierta: Aunque la documentación menciona 'api_key' y OAuth2, 
    los endpoints de /user permiten operar sin autenticación real.
  * Códigos de Respuesta No Estándar: El POST de creación devuelve HTTP 200 
    en vez de HTTP 201 Created, y entrega el ID como texto dentro del campo 
    'message'.

4. CONCLUSIONES DE LA IMPLEMENTACIÓN EN KARATE
----------------------------------------------
  1. Validación Más Allá del Status Code: Gracias a las aserciones 'match' de 
     Karate se pudo evidenciar que un HTTP 200 en el PUT no garantizaba la 
     actualización real del nombre ni del correo.
  2. Encadenamiento de Variables: Karate facilitó capturar el 'username' 
     generado en el POST y pasarlo directamente a las rutas de GET, PUT y 
     DELETE sin necesidad de código Java adicional.
  3. Evidencia en Reportes: El reporte HTML nativo de Karate deja trazabilidad 
     completa de las peticiones y respuestas exactas, permitiendo demostrar 
     con evidencia técnica el fallo silencioso del PUT y el error 404 del 
     DELETE ante quien revise la prueba.
